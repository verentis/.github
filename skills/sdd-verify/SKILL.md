# SDD — Verify

You are running the **verify** step — the review pass after `/sdd-implement`. Check that what was built actually satisfies the spec and **record a per-requirement verdict** the flow can act on. This is **review, not repair**: your only write is the verdict — you do not change the model or code. When gaps remain the user decides whether to heal them (the Heal action runs `/sdd-heal`, which fixes each failing requirement **in place**, one gap at a time, and never re-does the work that already passed); you just judge. Your gap descriptions **are** the healer's brief, so make them precise and actionable.

## Honour the solution's governance

When the spec's framework declares governance documents — Spec Kit's `.specify/memory/constitution.md`, say — `read_spec` returns them as `governanceDocuments` and the Specs panel lists them. **Read them first and treat their rules as binding on what you produce.** They are the user's standing constraints, not background reading. If a requirement and a governance rule genuinely conflict, say so and ask rather than silently picking one.

## What to do

**First, resolve the slug — never guess it.** If you weren't handed an exact slug, call **`read_spec` with no `slug`**: it lists every spec in the solution with its `slug`, `phase` and progress. Match what the user named against that list. Specs live under `intent/.specs/` and are reachable **only** through `read_spec` — never glob or grep the workspace hunting for spec artifacts. If nothing there plausibly matches what they named, `ask_user_question` offering the closest specs as options rather than inventing a slug.

1. Load the spec:
   - `read_spec(slug, artifact: "requirements")` — the EARS acceptance criteria (R1, R2, …), **and the framing sections above them**: the **Key User Journeys** (`UJ-N`) are what the criteria are trying to add up to, the **Glossary** is the vocabulary the model should speak, and **Non-Goals / out-of-MVP** is a boundary the implementation can violate just as easily as it can fall short of a criterion. An imported spec (e.g. a BMAD PRD) carries the same material under its own headings — `read_spec` returns the framework's own documents with `externallyOwned: true`, and they are **read-only** here: never write or normalize a `requirements.md` for such a spec. If the requirements themselves are wrong, say so and stop rather than fixing them in place.
   - `read_spec(slug, artifact: "design")` — the intended model changes + realization plan.
   - `read_spec(slug, artifact: "traceability")` — which tasks/elements/files were meant to satisfy each requirement. Compact per-requirement target summaries by default; `read_spec(slug, artifact: "traceability", requirementId: "R3")` for one requirement's full targets.
   - `read_spec(slug, artifact: "coverage")` — the covered/uncovered/stale/broken rollup: summary + one compact row per requirement (`id`/`title`/`status`/`linkCount`), **no** per-target arrays. Narrow to the failing ones with `status: "gap"` (or `uncovered`/`stale`/`broken`/`covered`), and drill into one requirement's full targets with `requirementId: "R3"`.
   - `get_change_review(section: "traceability", specSlug: "<this spec>")` — the **change side** of the same question, and the one input here that is computed rather than judged. `coverage` walks from each requirement out to its links, so it can only ever see a requirement nobody linked; it is structurally blind to the opposite failure — a designer element or hand-written file that was changed for this feature and that **no requirement points at**. This is the deterministic review the Changes Review tab renders, over the merge-base → working tree range, so committed waves and the worktree are both in it. It returns a compact text report: the traced map (spec → requirement → the changes realizing it, `[stale]`-marked) followed by the `untraced elements` and `untraced custom files` lists. Read it before you judge anything: it tells you where to look as well as what is missing.
     - **Always pass `specSlug`** — it names the one spec whose requirements get expanded. Every other spec in range is reported as a name plus its requirement count, and omitting `specSlug` expands none of them. The untraced lists stay solution-wide either way, because they are the gate.
     - Rows are **rolled up into their parent**: a row ending `(+N child change(s))` is **N+1 changes**, not one — the parent plus N of its attributes / fields / operations that changed too. Read it as a group when you resolve it, and don't mistake it for a single finding.
     - Every list is capped (`maxRows`, default 200) and any overflow is stated in the output — if you see rows omitted, re-run that section with a higher `maxRows` before judging, rather than treating the visible rows as the whole set.
     - Check the range line in the feedback. When no base branch could be resolved (a solution sitting on its own trunk, a single-branch clone) the review falls back to a HEAD baseline and says so — that range covers **only the working tree**, so committed waves are invisible in it. Re-run with an explicit `refA` (the commit the spec's work started from) or `baseBranch` before you conclude that anything is untraced or missing. Whichever range you settle on is the one `record_spec_verdict` stamps: it reuses the range of your last `get_change_review` call in this conversation, so you do not have to repeat it (you may still pass `refA` there to override). A range whose refs aren't a walk from an older baseline to a newer comparand — reversed, or two diverged branches — is also called out on that line; the diff is correct, but added work reads as deleted in a reversed one, so fix the range rather than judging from it.
2. Verify, per requirement:
   - **Model**: `get_designer_validation_errors` is clean; the designed elements/associations exist (`find_designer_elements`, `get_designer_element_details`).
   - **Coverage**: every requirement has ≥1 trace target, spanning **both** what realized it — every model change it drove (the designed elements/associations) **and** every custom-code file written for it must be linked. Flag `uncovered`, `stale` (requirement text changed since it was linked), and `broken` (a linked element/file no longer resolves against the saved model / disk — `read_spec(slug, artifact: "coverage")` now computes this, matching the Specs panel). A `broken` (or `uncovered`) requirement — including one whose model is linked but its custom code isn't, or vice versa — is a coverage gap: record it as a **`gap`** verdict whose `actual` names the missing/unresolved target, so `/sdd-heal` re-records the corrected link. Because `complete_spec_task` refuses to tick a `[model]`/`[code]` task while its designer is unsaved **or while any of that task's recorded links is broken**, and `record_spec_traceability` rejects a target that doesn't resolve rather than storing it, a wave that reached "all ticked" implies its links resolved at the time. So a `broken` link at verify time means it broke **after** the tick — a later rename or delete, or a hand-edited `traceability.json` — and an `uncovered` requirement usually means a rejected link was never re-recorded. Both are still gaps; the distinction is what the healer should go looking for.
   - **Untraced changes — the deterministic gate.** Every row under the change review's `untraced elements` / `untraced custom files` is a change that was made and that nothing claims. **Resolve each one, and say which way you resolved it** — leaving them unmentioned is the failure this step exists to prevent. There are exactly two allowed outcomes per untraced change: either it **realizes one of this spec's requirements** (the wave just never recorded the link) — record a **`gap`** on that requirement, naming the untraced element/file in `actual` and `location` so `/sdd-heal` records the missing link, attributing it via `design.md` / `tasks.md` — or it **belongs to other work** (a different spec, a manual fix, an unrelated refactor sharing the branch) — record no gap, and name it in your chat report as out-of-spec work. The range is solution-wide, so the second outcome is normal, not a failure. Two things are deliberately **not** untraced findings and never appear in the lists: a deleted element (nothing is left to link) and a `FullyManaged` file (generated output — its traceability belongs on the model element that produced it). Conversely, when the report warns that a designer's element diff failed, the element list is **incomplete** — say so rather than reading it as clean.
   - **Code**: spot-check the generated + hand-written code against the criteria (`read_file`) — does the behaviour each criterion describes actually exist?
   - For a large area, you may dispatch a `discovery` sub-agent to map it read-only before judging. Several requirements can be mapped at once: emit the `create_sub_agent` calls in a **single response** and they run concurrently, one explorer per requirement or per area, each with its own focus.
3. **Then verify the journeys, not only the criteria.** Criteria pass one at a time; a user journey is what they are supposed to add up to, and a feature can satisfy every criterion and still have no working path through `UJ-2`. Walk each `UJ-N` beat by beat against what was built — entry state, each step of the path, the climax, the resolution, and its edge case — and check there is a real operation / endpoint / interaction behind each beat. A journey with a missing or dead beat is a **`gap`**, recorded against the requirement(s) that name it under `**Realizes:**` (or the nearest owning requirement when none does), with the broken beat in `actual`. While you're there, flag anything built that lands in **Non-Goals** or out-of-MVP scope — that's a gap too, and the healer's brief is to remove it, not to add more.

## Challenge every gap before you record it

A false `gap` is expensive: `/sdd-heal` turns each one into a repair task, so a mistaken gap sends the healer to change working code against a requirement it already satisfies. Before recording, **try to disprove each candidate gap** — passes need no challenge, only the gaps do.

Dispatch one `discovery` sub-agent per candidate gap, **all in a single response** so they validate concurrently, each briefed to argue the opposite case:

> Requirement `<id>` is claimed to be unsatisfied because `<candidate reason>`. Read the model and the code and try to show it IS satisfied — the behaviour exists somewhere the reviewer didn't look, the element is linked under a different id, the criterion is met by generated code rather than hand-written code, or the reviewer misread the criterion. Report `refuted` with the exact element id / `file:line` that satisfies it, or `confirmed` with precisely what is missing.

Then:

- **Refuted with evidence** — record it as a `pass` and cite that evidence in your report.
- **Confirmed** — record the `gap`, and fold the validator's specifics into `actual` / `location`; a challenged gap gives the healer a much sharper brief than an unchallenged one.
- **Inconclusive** — record the `gap`. When you genuinely cannot tell, a gap is the safe verdict; say in the report that it was inconclusive.

**Traceability gaps skip the challenge entirely** — both the `broken`/`uncovered` ones `read_spec(slug, artifact: "coverage")` computed and the untraced changes `get_change_review` computed. They are already machine-checked: a link either resolves or it doesn't, and a changed node either carries a requirement ref or it doesn't. There is nothing for a sceptic to refute, so dispatching one only burns a turn. Record them directly. The one judgement left on an untraced change is **attribution** — whether it belongs to this spec or to other work — and that is yours to make from `design.md` / `tasks.md`, not a validator's.

## Record the verdict, then report

1. **Record the machine-readable verdict.** `record_spec_verdict` is available in **every** session type — a panel-fired review, an in-app chat, or an external ACP harness — so recording the verdict is always the required output of this step, never something to skip because no panel is watching. Call `record_spec_verdict(slug, results)` with one result per requirement. A **pass** is just `{ requirementId, verdict: "pass" }`. A **gap** carries the healer's brief — `{ requirementId, verdict: "gap", reason, expected, actual, location }`:
   - `reason` — a one-line summary of what's missing or wrong.
   - `expected` — what the acceptance criterion requires (the target behaviour the fix must produce).
   - `actual` — what is actually there now: the specific deficiency (missing, wrong, or a broken/absent element).
   - `location` — where to fix it: the file(s) and/or model element(s)/operation(s) involved.

   Mark `gap` whenever the behaviour the criteria describe isn't genuinely there **and the challenge above didn't refute it**; when unsure, prefer `gap`. **`/sdd-heal` reads these fields straight from `verdict.json` as its brief** and turns each gap into one repair task — so `expected`/`actual`/`location` must be precise and actionable, not vague. A weak brief produces a weak fix; leaving them blank leaves the healer guessing.

   `record_spec_verdict` **re-runs the change review itself** and stamps the range, the counts and the untraced lists into `verdict.json` beside your results. That section is not taken from you and you cannot omit it — so if it still reports untraced changes after an all-pass verdict, the tool says so in its feedback and the record shows it either way. Treat that feedback as a prompt to correct the verdict, not as noise.

   It re-runs over **the range you reviewed**, not a fresh default: the range of your last `get_change_review` call in this conversation, or `refA`/`refB`/`baseBranch` if you pass them there (which wins). The record says which of the three it used, so don't restate the range by hand unless you mean to change it. If the range it stamped was narrowed, the feedback says that too — an empty untraced list over a working-tree-only baseline is a much weaker result than an empty one over the branch's merge-base, and if that is what you got, widen the range with `refA` and record again rather than reporting it as clean.

2. **Report in chat too.** Summarise the per-requirement verdict for the user, each citing its evidence (an element id, a file, or the missing piece), note how many candidate gaps the challenge pass refuted, and list the concrete gaps — call out any traceability problems (uncovered, broken links, stale or mis-linked traces) alongside the behavioural gaps.

   State the **change review** result explicitly too, because it is the part the user cannot reconstruct from the verdict rows: the range reviewed, how many changed elements and code files it covered, how many requirements they realized, and — one line each — every untraced change with how you resolved it (which requirement's gap it became, or why it is out-of-spec work). If nothing was untraced, say so in a sentence; that is a real result and worth stating plainly.
3. **Then, and only on a CLEAN verdict, offer the final gate.** When **every** requirement passed, call **`advance_spec_phase(slug, artifact: "tasks", toPhase: "done")`** — the last gate of the flow, and it works from every surface. In-app it raises an approval card and blocks until the user decides; under a spec whose manifest carries `gates: auto` it advances immediately. On **reject**, take the user's feedback as the review they want redone rather than advancing. Phases advance **one gate at a time** (the tool refuses a jump), so this moves the spec from **verification** — the phase you are running *in*, which a spec enters by itself once its last task is ticked — to **done**.

   **With any gap, do NOT advance** — the spec stays in verification, which is exactly where the review loop belongs. Report the gaps and stop; the heal flow fixes them (the Heal action runs `/sdd-heal` to fix each gap in place), then verify runs again. Change nothing else either way.
